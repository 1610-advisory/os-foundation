# Changes

Plain-word release notes for os-foundation. Newest first. Versions follow semver. Your folder records its version in `os_version:` in `company-profile.md`.

## v1.0.2 — unreleased

Five small fixes from the first team upgrade on v1.0.1.

- **Setting the review key never shows it.** At a terminal, `host.sh set-secret` asks `OS_REVIEW_KEY:` and reads with no echo, so the key is not on screen or in scrollback. A pipe still works. An empty value stops with one line. The `review-command:` line and add-teammate A3 give the same command, with the host and org in front.
- **`me` is the person signed in here.** `team-on` writes the config `me` file for the person whose login this computer signs in as, not always the admin. Another org owner, such as an outside advisor, can run it. When no person matches, it writes no `me` and says how to fix it, so `sync push` does not stop with `identity mismatch`.
- **A v0 job title is kept.** v0 people pages used `role:` for the job title. `team-on` and `add-person` move it to `job_title:` before they set the OS role.
- **An org invite is named.** On GitHub, adding someone outside the org to a team sends them an org invite. `team-on` and `add-person` say so in one `invite:` line. `join` stops while the person's invite is still open and gives the link that accepts it.
- **The check comment shows the gates.** The pull request comment starts with `secret scan: pass, lint: pass` above the model review.

## v1.0.1 — 2026-11-01

A small release: one more review vendor.

- **OpenRouter can run the model review.** Set `vendor=openrouter` in `.github/review.conf` (or `review_vendor=openrouter` in the `add-teammate` or `upgrade` answers). One OpenRouter key reaches many vendors' models. Name the model as OpenRouter does, `<maker>/<model>`; a blank model uses `openai/gpt-4o-mini`. For `second-vendor` or `same-vendor`, the vendor is the model's maker. A failed review names OpenRouter's message, never the key. A reply with no verdict but an error message now says that message too.
- **The upgrade writes `os_version: v1.0.1`.** The check tools are release `2026110206`, so `upgrade --refresh` brings this review script to `main`.

### Also in v1.0.0, listed here late

These shipped in v1.0.0 but were missing from its notes.

- **Moving off v0 on Windows.** `join` reads a file the old folder checked out with Windows line ends as the same text, so only the real edit is set aside.
- **Moving off v0 is careful with names.** `join` never brings a file whose name has `..`, a leading `/`, a tab or a new line, or one that would go through a link. It says so in one line and never says the old folder may be deleted.
- **A file a commit added and the folder later lost still comes over.** `join` brings it from the commit. A link or a special file is named and left in place.
- **A stash is part of the delete rule.** While the old folder has a stash, `join`'s last line and `sync.sh status` say to redo each stash here before deleting the old folder.
- **The jobs find the right tools.** Tool folders go before the system folders in `PATH`. A Mac with only the Xcode stand-in for `git` gets "git not installed: install the Xcode command line tools, or run join again". A missing tool shows in `sync.sh status` and the sync log.
- **No false squash error.** When `main` already has the same text from another computer's sync commit, `pull` drops the copy here quietly.
- **`join` starts the jobs on a Mac.** It loads them in launchd at once (`OS_JOBS_LOAD=0` turns this off). Uninstall stops them.
- **The weekly report reaches the host.** The reports run makes its `reports/` folder first.

## v1.0.0 — 2026-11-01

The multi-user release. A solo owner gets a simpler setup. A team gets enforced review, private workspaces and nightly sync.

### New for everyone (solo too)

- **One setup step fewer.** The `.agents/skills` and `.claude/skills` links now ship in the folder. You no longer link them by hand.
- **Logs are plain files.** Each person writes one short log per day in `memory/logs/`. There is no separate `logs` branch any more.
- **Level and switches.** `company-profile.md` says the level (`solo`, `team` or `app`) and which switches are on. Agents skip rules for a level or a switch that is not on. Every switch is off by default.
- **`privacy.md`.** A script writes it from your level and switches. It lists every place a copy of your data sits, and only the places that are on: who can read it, how long it stays, how it is removed.
- **`scale.md`.** A reference for large companies: scale switches, the projects pattern, a checklist for outside parties' computers, and the 5,000-staff case with results from a local Forgejo load check. Agents do not load it at start.
- **Versions.** `1610.sh/os` serves the latest release. `1610.sh/os@vX.Y.Z` serves a pinned one. `lint` can say in one line when a newer version exists. You choose when to run the new `upgrade` skill. The new `privacy` skill writes `privacy.md`.
- **The folder can keep its own copy.** A new `library/` keeps raw text exports and full transcripts, for each source a person chooses to copy. It is its own private repo: only the owner and admins have it, and teammates read the summaries in the wiki. `memory/existing-sources.md` records each source's mode (`index` or `copy`), where it is edited, and its retention. `ingest` puts full transcripts in the library, only for an admin (from `me`); a meeting note keeps the summary, decisions and action items, never a full transcript. Git holds text only: photos, audio and video stay on one computer for now.
- **`upgrade` brings the v1 rules to a set-up folder.** `AGENTS.md` and `CLAUDE.md` (company and areas) get the v1 rules. Every line the company added is kept as written, under the matching v1 heading, or in `company-rules.md` when the file would be too long.

### New for teams

- **Sync commits in the folder (the v1 redesign).** Sync now uses git the plain way: the folder commits the notes that pass the checks on `main`, with a `Sync-Seat:` line naming the computer, and pushes them to that computer's own branch `sync/<person>/<computer>`. Nothing is rebuilt or force-pushed. The pull request merges with a merge commit, and the next pull is a fast-forward. Two computers of one person have two branches and two pull requests. A copy here that `main` already has is dropped by the pull, so a merged note, a merged delete, or a rules file whose own pull request merged never blocks a pull again. Push takes the host's changes first, so a file merged meanwhile is no change. A commit made by hand stops that repo with one plain line. `sync.sh status` says how many changes are not on the host yet. `join` commits the terms page and runs `sync.sh push`. `remove-teammate` deletes the person's sync branches. A squash merge on the web is caught: nothing is lost, the folder takes `main`, and one line asks the admin not to squash. A folder made by the old code moves over on its first pull and push: loose copies go, real work stays, and the old `sync/<person>` branch and its pull request are closed.
- **Changed under you: the agent re-applies, git never merges two people's text.** When a file changed here and on the host before either merged, sync keeps the person's version aside with the text it started from, takes the host's text, and holds the file (`re-apply`). At the next session the agent makes the person's change again on the new text (`skills/sync/re-apply.md`). When the two changes disagree, it asks the person: in chat, or by a line in their inbox, a comment on the pull request and the nightly digest. A delete on one side and an edit on the other is the same case.
- **Sync never puts back old text or sends conflict lines.** After a squash merge, the folder takes `main` for every file `main` changed, so a teammate's note merged since is never undone by the next push; if it cannot, nothing is changed, set aside, committed or sent. A both-changed file is set aside only once `main` is in. If the old branch on the host cannot be deleted, the next push deletes it first (only when `main` already has its work). A merge a crashed run left open is undone first. A file that still has conflict lines (`<<<<<<<`, `>>>>>>>`) is held. A name with an accent, an em dash or an emoji is matched like any other.
- **Offline, push still saves.** When the host cannot be reached even to check who is signed in, push commits the notes here and sends nothing; `status` counts them (`1 change here is not on the host yet`) and the next push sends them. A pull or push that goes through clears the last error, whatever left it. A sync commit of many files is `Update <n> files` with a line per file, and the join commit names the person.
- **A bot run never moves the folder.** It works in a temporary worktree on `sync/<bot>`, so the folder stays on `main` and its pull and push go on. A run that could not push keeps its commit: the next run builds on it.
- **After an upgrade on a host, pull puts the folder back on `main`.** The upgrade leaves the folder on `upgrade/v1` (areas on `upgrade/scripts`) until its pull request merges, and says so in an `admin:` line. Once it merged, `sync.sh pull` moves each one back to `main`; before that it says what it waits for.
- **Team-on after an upgrade sends its rules by pull request.** When `main` already has rules, a new area director used to stay in the admin's folder and never reach the host. Now team-on opens one rules pull request with the `CODEOWNERS` and review files it changed, and keeps any line the company added.
- **A team upgrade adds `review-rules.md`.** A v0 company had none, so after the upgrade the review fell back to the default rules. The upgrade pull request now adds the template's file, and never replaces one the company has.
- **The model review skips stock text.** A file exactly as this release ships it is left out of the review (an older release's text is reviewed); the list comes from the check tools on `main`, never from the pull request. A refresh puts this release's check tools on `main` first, so its pull request passes on its own. When a pull request is still too large, the run prints the exact `/override` comment.
- **An upgrade pull request explains itself, and the review knows it.** The upgrade body opens with what it is (the release's rules text, with the company's own lines kept), lists each company line it kept, and says what moves between approval tiers and why (the release's default). Before the pull requests, the upgrade puts the release's `review-rules.md` on `main`, so the review judges them with rules that know the upgrade; the head still cannot change those rules, because the checks copy them from `main`. When a review fails a pull request the admin opened through upgrade, refresh, team-on, add-person or remove, the step has already printed the exact `/override` comment, and the review's failure names `/override <reason>` too.
- **Code owners stay the same on GitHub and Forgejo.** Team-on's rules pull request says what changes and why, and keeps the admin as an owner. `.github/CODEOWNERS` and `.gitea/CODEOWNERS` name the same owners, so on Forgejo an area rules change needs both the director and the admin. When a person leaves, `remove-teammate` takes them out of every `CODEOWNERS` they are on, in the company and each area; a line they owned alone gets the admin.
- **Refresh tidies up after itself.** It fetches with `--prune`, says what the host answered when a fetch fails (not "could not reach" when it did reach), and closes the admin's own open refresh pull request for an older release, with a comment that names the new one.
- **Offline is two lines, not one per repo.** An offline push prints one line for the push and one for the pull. When the push check itself has no network, the notes stay in the folder, out of any commit, and go up at the next online push.
- **`upgrade --refresh` for a v1 company.** It brings the stock skills and checks to a newer release: one rules pull request per repo (one commit at solo). Only files that are exactly as some release shipped them are replaced; a file the company changed is kept and listed for the admin, and the company's own skills are never touched. Before this, a v1 company could not take a fix at all.
- **The checks job uses `actions/checkout` with full history.** Pinned by commit, no token left in the folder. The check tools come from `main` as it is now, never from the pull request (D26). Checks run only for a pull request into `main`: an `/override` comment on a pull request into any other branch is refused before anything runs, so a branch cannot bring its own check tools. An `/override` comment reads the pull request's own commits, and on GitHub it re-runs the failed checks run, which then passes: the required `checks` status turns green. On Forgejo the job image needs Node.

- **`add-teammate` turns on the team level in one run.** The company folder, areas and one private workspace per person go to your company's GitHub (Team plan) or Forgejo, with their history.
- **Nobody writes to `main`.** Each computer has one branch (`sync/<person>/<computer>`) and one standing pull request. Notes merge by themselves when the checks pass. Rules files go by their own pull request and need their owner's approval.
- **Checks on every pull request:** a secret scan, `lint`, and a review by a second AI model against `review-rules.md`. All checks run in one job to keep host minutes low.
- **`sync` and OS jobs.** Pull every 15 minutes. Push each night, after a secret scan and a commit-or-hold check by a small model. Any failed step pushes nothing.
- **`sync pull` checks first and pulls only what changed.** One full pull runs each day. On Windows, a pull with nothing new does not start Git Bash.
- **Nightly review and reports.** On the admin's computer: clear errors fixed by pull request, one daily digest of flags per approver, a daily "to decide" list and a weekly report.
- **Joining terms and leaving.** `joining-terms.md` holds the delete promise each person accepts when they join. `remove-teammate` removes access first. A helper then deletes the company folder from that person's computer. Leave, holidays and offline days never trigger it.
- **Checks run on GitHub.** The checks job now signs in to git with the form GitHub accepts (basic auth with the job token), so every pull request gets its `checks` status. Before, it failed at checkout on GitHub and nothing merged. Forgejo accepts the same form.
- **Team setup and the v0 team upgrade work on GitHub on a second run.** An existing repo or team is reused. A repo left empty gets its first push before protection. A refused push or a missing `gh` scope says the cause in one line. A Free GitHub org stops before any change: team setup needs GitHub Team. A plan the sign-in cannot see stops too: sign in as an org owner. The upgrade puts the check tools on `main` first and never leaves `main` unprotected, even when that push is refused. It keeps every `CODEOWNERS` line the company added. Any stop while protection is lifted puts it back, or says plainly that `main` is open. On Forgejo every upgrade pull request gets auto-merge. On GitHub the admin's own rules pull requests need one bypass click, so they get no auto-merge (that would hide the bypass box), and the upgrade prints the click. It says `upgrade: ok` only when nothing is left to merge by hand. A dry run on a Free org reports the plan as a finding and still prints the full report.
- **Safer daily path for teams.** Setup and offboarding scripts commit only the files they changed, so an untracked or held file never goes up by accident. A new teammate's folder stays on `main` after joining, and `pull` moves an older folder off its own sync branch once its work is on the host. Logs and an area's shared `drafts/` folder go to the area as the rules say. The joining terms pull request merges by itself. A failed pull says why in one line, and `sync.sh status` shows it.
- **Upgrade fixes from a real v0 company.** The logs move finds `origin/logs` in a fresh clone and stops on a stale local `logs`. Other v0 clones move their old logs worktree out on `pull` or `join`, without losing a log. If that move stops part way, it says so in one line and names the folder that holds a full copy. The old logs land in `memory/logs-archive/`, outside the old logs folder, and `sync push` keeps new logs off `main` until the admin deletes the old `logs` branch, so a plain `git pull` on an old copy writes nothing inside that folder. The upgrade prints a log freeze before the run and the safe steps for teammates after it. When two people logged on the old branch, the move merges their logs first, and a real clash stops with the exact steps. Logs pushed to the old branch after the upgrade reach `main` by the next full `sync pull`. That catch-up never writes over a file: a different copy already there keeps its place, and the old text goes beside it as `<name>.old-branch.md`. If the old branch changes again, the new text gets its own name beside it. A failed catch-up is a pull error with one plain line. When the move merges two people's logs, both changes reach `main`. A file changed here never makes the move write older logs over the archive: only that file keeps the person's copy, with the other text beside it. If that move cannot put a file back, the old logs folder goes back as it was, so the next run keeps the edit. An edit made in `memory/logs-archive/` and not committed is never written over: the old folder's copy goes beside it. `sync push` asks the host about the old `logs` branch on every push, so a branch an old copy pushed back still holds new logs. The upgrade skill gives one clear order for a team after the merge: the admin runs Part A again, then each teammate saves their logs, renames the old folder and joins in a new one (on Windows in Git Bash). The rules merge drops the setup placeholder only in the part that got company lines, keeps a blank line before each heading, carries a table row with its header, and keeps v0 lines out of the wrong subheading. A merged `AGENTS.md` over 9,000 characters gets one line on what to move. Every area gets `.gitattributes`. A profile with no host gets `host: none`, and `lint` flags a missing `host:`. The rollback steps on a host also undo the check tools commit and the v1 rules.
- **Moving off v0 keeps unpushed work, and the old logs branch can go.** `join` finds the renamed old folder beside the new one and lists each file and commit in it that the host does not have (`old-folder:` lines, the company and each area, and its old logs folder). It never deletes it. The upgrade's teammate line says to copy that work before deleting the old folder. v0 protected the `logs` branch against deletion, so `git push --delete` failed: the new `host.sh drop-logs <repo>` lifts that one rule and deletes the branch, and the upgrade's `admin:` line names it for each repo. It never touches `main`, and a second run is safe.
- **Rules and owners fixes.** Before an upgrade pull request, `main` gets only the release's `review-rules.md`, never a copy in the folder (a company's own file goes up in the pull request, which the review judges). A `#` comment on a `CODEOWNERS` line is not read as owners, and remove keeps it. An add-person pull request that names an area director changes `CODEOWNERS`: on GitHub it says merge by hand (auto-merge off), on Forgejo it turns on auto-merge. When remove cannot reach an area, it names the area, ends `remove: not finished: <areas>` and exits 3, never `remove: ok`. The upgrade's `company-lines=` and the pull request body count the same lines: no blank lines, and no stock v0 heading. team-on no longer shows `gh: Not Found (HTTP 404)` before it creates a repo.
- **Moving off v0 and offboarding hold up when run again.** `join` reads a renamed v0 folder's old logs through that folder's own `.git` (v0's logs link names the old path), lists only real log commits as logs, and tells you to copy each log into `memory/logs/`, never to push the old branch. When it cannot read a part, it never says the old folder may be deleted. The teammate steps save the logs before the rename, in each area too. `remove` can run again until it is done: an archived workspace is done, a repo whose offboard change is on `main` says `already done` (no empty pull request), an old offboard branch goes, and the areas it missed get their pull requests. `drop-logs` reads the repo first and checks the branch is really gone; if the rule went and the delete failed, it says so. A refresh no longer calls the generated stock lists company-changed, and names `drop-logs` while an old `logs` branch is on the host.
- **Moving off v0 brings the old folder's work over itself, and the Mac jobs find their tools.** `join` now copies each new file and log from the renamed old folder into the new one (it makes `memory/logs/` when an area lacks it), and sets each changed file aside so the agent re-applies the change to the host's current text. A whole-file copy could undo a colleague's newer line on `main`. It lists a stash, reads both the checked-out logs commit and the `logs` branch, and follows a renamed log. Logs that `pull` brings into `memory/logs-archive/` are never held as "belongs in the workspace". The OS jobs carry the `PATH` that join saw, and sync finds Homebrew and `~/.local/bin` tools even from launchd. A missing tool is named (`claude not found: install it, or run join again`), never "could not reach the host". The upgrade skill says which copy of `upgrade.sh` to run.
- **Retries and holds that keep work.** A refused switch back to `main` never stops `join`, `add-person` or `remove-teammate` before the pull request, and a second run opens it. A second `join` also pushes the joining terms a stopped run left out. Offline, it stops and says to run it again, instead of guessing. `pull` never swaps in a fresh copy while any local branch has a commit the host never had. A good push never clears a pull error. The daily jobs leave the temp folder as they found it: each run of `sync`, the host, team, nightly, bot and check scripts keeps its temp files in one folder that goes when the run ends or is stopped, with one sign-in helper file per run.
- **A failed model review says why.** It names the HTTP code (or the network error) and the vendor's message, never the key. A review key pasted with a space or a line break still works.
- **Who approves your own rules change, said plainly.** On GitHub the author's own approval never counts. A director's own area change needs the admin. The admin merges their own with the bypass box. On Forgejo your own change merges on green checks.
- **Area templates keep each row in its own table.** The `apps` area's skill row moved out of the approval tiers table. A test checks every rules table.
- **Windows sync works through Git Bash.** The jobs run the same `sync.sh` from Task Scheduler, with no window. Tested on a Windows runner (S15).
- **New skills:** `sync`, `remove-teammate`, `remove-leak`, `company-skills` (for chat-only agents).
- **Bots (switch).** `add-bot` gives a bot its own GitHub App and one-hour tokens. Every bot commit carries a run ID, and `undo-run` reverts one run in one step.
- **Bot runs push their own branch.** A bot run sends the commits already on `sync/<bot>`, run id included, and opens `sync: <bot>` as the bot. It does not commit that work again as the person. A secret or a rules file in that range pushes nothing.

### Not in v1

- **The dream pass.** Hidden until it has run on real knowledge long enough to trust it.
- **The connector.** Readers without a GitHub seat and the app level need the 1610 OS app, which is a separate release.
- **Projects as a feature.** The pattern is written up in `scale.md` only, until a pilot shows it helps.
