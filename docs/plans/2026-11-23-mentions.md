# Plan: mentions in logs instead of report pages

Status: **draft for review. No template change yet.** Target: the release after v1.0.7.

## 0. The idea in five lines

1. Anyone writes `- [ ] [[Jane Doe]] review the price list` in a log or note in an area.
2. At session start, a small script looks through every repo on that person's computer for open to-dos that name them. The agent tells the person first.
3. Ticking the box (`- [x]`) closes it. No report file, no gate exception, no empty page.
4. Reports and notes for a person live in areas, never at the company root. A company-wide item is one pointer line in the root `AGENTS.md`.
5. A Claude Code plugin does the same steps with hooks. It is optional. Other agents follow `AGENTS.md`.

Why it fits: access comes free. A person searches only the repos they have, so they see only mentions in areas they can read. The pull job runs every 15 minutes, so a mention arrives within 15 minutes of the author's push.

What is in the template today (v1.0.7):

- `AGENTS.md` section 2: at session start run `sync.sh pull` and `sync.sh status`. "No vendor hooks."
- The admin job at 03:30 runs `nightly-review/run.sh`, then `reports/run.sh` (`sync/jobs.sh`).
- `reports` writes a daily to-decide page per area, a weekly page per area, and the company pages in `areas/<report_area>/reports/` (#66).
- The nightly review folds logs older than 30 days into `memory/logs/YYYY-MM-summary.md` and deletes the daily files from `main`.
- `template/AGENTS.md` is 8,953 characters. The cap is 9,000. Every line we add needs a line removed.

## 1. Mention format

### Lock: a wiki-link to the person's page, first thing after an open box

```markdown
- [ ] [[Jane Doe]] review the Q4 price list due:2026-11-28
- [ ] [[Jane Doe]] [[Sam Lee]] agree the new intake form
- [x] [[Jane Doe]] review the Q4 price list due:2026-11-28 done:2026-11-26
```

Rules:

- **A mention is an open box (`- [ ]` or `* [ ]`), then one or more `[[...]]` links, then the ask.** The links must come first. `- [ ] call [[Jane Doe]] about the invoice` is a to-do *about* Jane, not *for* Jane. The finder ignores it. This one rule removes most of the noise.
- **The link is the person's page name** (`people/Jane Doe.md`), with or without an alias: `[[Jane Doe|Jane]]` counts.
- **Who can be mentioned:** teammates only. That is a page in `people/` with a `slug:`, and no `left:`. A customer contact has no `slug:`, so a link to them is never a mention.
- **Due date (optional):** `due:YYYY-MM-DD`, anywhere on the line. Plain text, easy to grep, and easy to type.
- **Done:** tick the box. The agent may add `done:YYYY-MM-DD`. Never delete the line: the log is the record.
- **Who asked:** the log file name says it (`YYYY-MM-DD-<slug>.md`). In other notes, `git log` says it. No `from:` field.
- **Reply:** the person ticks the box and, if they have more to say, writes a new mention back: `- [ ] [[Sam Lee]] done, see [[Price list 2026]]`.

Why `[[Full Name]]` and not `@slug`:

- It is already the house link style (`AGENTS.md` "Conventions").
- In Obsidian it is a live link. The person's page shows every mention in its backlinks panel, for free.
- Obsidian rewrites the links when a page is renamed.
- Cost: a name is longer than a slug, and a name can change. The finder handles that with `aliases:` (section 3).

### Where mentions may live

| Place | Mention? | Why |
|---|---|---|
| An area: `memory/logs/`, meetings, notes, project files | Yes | The normal place. Both people must have the area. |
| The person's own workspace `users/<me>/` | Yes, to yourself only | Only you have that repo. A private to-do list. |
| Another person's workspace | Never seen | Nobody else has that repo. |
| The company root | No | The root holds no logs or notes (review check 7, sync 6a). |
| `skills/`, `templates/`, `.claude/`, `reports/` | Ignored | Examples and generated pages. The finder skips them. |

### Company-wide items

One line in the **"Right now"** list of the root `AGENTS.md`, which every agent reads:

```markdown
- Everyone: read [[2026-11-23 New holiday rules]] in `areas/everyone/` by 2026-11-30.
```

- The file it names lives in `areas/everyone/`, which every teammate has. If the company has no `everyone` area, the item cannot be company-wide: ask the admin.
- The line is a root rules change, so it goes by `propose` and an owner's `/approve`. That is right: few items, and an owner says yes.
- The admin removes the line when it is no longer needed. "Right now" keeps its cap of five lines.

## 2. The session-start finder

New company skill: `template/skills/mentions/` with `SKILL.md` and `mentions.sh`. Bash, no dependencies other than `git`, `grep`, `awk` and `sed` (Git Bash on Windows has all four).

### What it does

1. Find the company root: walk up from the current folder to the folder with `company-profile.md`.
2. Read who I am from `~/.config/<company>-os/me` (the same file `sync` uses). Never from a repo file or a chat. If it is missing: print `mentions: who you are is not set` and exit 0.
3. Find my page in `people/`: the page whose `slug:` is me. Take its page name and its `aliases:`. At `solo`, the only person is me.
4. List the repos on this disk: the company root, each `areas/<area>/` that is a git repo, and `users/<me>/`. **Only what is on disk.** No host call, no network.
5. In each repo, run `git grep -n -E` for the mention pattern on `*.md` files, tracked and untracked, but not ignored. Skip `skills/`, `templates/`, `.claude/`, `.agents/`, `reports/`, `bots/`.
6. Drop lines inside fenced code blocks (one small `awk` pass over the files that matched).
7. Parse each hit: repo, path, line, author (from the file name, else `git log -1 --format=%an`), age in days (from the file name date, else the commit date), `due:`, and the ask text.
8. Sort: overdue first, then due soonest, then oldest. Print.

The pattern (names escaped for `grep -E`):

```text
^[[:space:]]*[-*][[:space:]]+\[ \][[:space:]]+(\[\[[^]]+\]\][[:space:]]*)*\[\[(Jane Doe|Jane|J\. Doe)(\|[^]]*)?\]\]
```

### Output shape

Plain text, one fact per line, stable so a hook and a test can read it:

```text
mentions: 3 open for jane (areas: sales, ops)
- overdue 2d: areas/sales/memory/logs/2026-11-20-sam.md:14 (sam) review the Q4 price list due:2026-11-21
- 3d: areas/ops/meetings/2026-11-20 Weekly ops.md:31 (lee) agree the new intake form
- 9d: users/jane/memory/logs/2026-11-14-jane.md:5 (jane) renew the domain
and 2 more older than 14 days: say "show all my mentions"
```

- Nothing open: one line, `mentions: none open for jane`.
- At most 10 lines. Then `and N more ...`.
- `--count`: prints only the number (for the status line and hooks).
- `--all`: no cap, old items too.
- `--json`: one JSON object per line, for the plugin and the app. Built with `printf`, no `jq`.
- `--for <slug>`: for the admin's nightly job only (section 4). A normal session never uses it.
- Exit 0 always, even on a broken repo (it prints `mentions: <repo> not read` and goes on). A session must never stop because of it.

### Speed

- `git grep` uses the index and many threads. On a test company with 20 areas and 50,000 markdown files it should finish in under 1 second on a laptop. The test suite checks a budget of 2 seconds (section 6).
- Only `*.md`, only lines that start with a box, so most files do no real work.
- Every repo runs with a 5-second limit. A slow repo prints `not read` and the rest go on.
- Cache: the 15-minute pull job runs `mentions.sh --count --cache` after a pull that changed something. It writes the count and the list to `.git/os-foundation/mentions-<me>` (like `pull-state`: never committed). The status line and hooks read the cache, so each turn costs nothing.

### Access

- The finder reads only folders on this disk. A person without an area does not have it, so they never see its mentions.
- It reads the working copy, so it sees the person's own notes before they are pushed. That is fine: they are the person's own.
- Lost access: the helper job counts days without access and deletes the area on day 14. Until then the folder is on disk and old. The finder adds `(no access: not updated since <date>)` to hits from that area. It reads the helper's state file to know.

## 3. Edge cases

| Case | What happens |
|---|---|
| **A mention in an area the person cannot read** | Never seen. So the author's agent checks first: the person's page lists `areas:`. If the area is not there, the agent says "Jane cannot read sales. Write it in an area you both have, or tell her another way." `lint` reports each such mention. The nightly review flags it to the author. |
| **Renamed person** | When a page is renamed, the old name goes into `aliases:` on the page (the rename step in `add-teammate` and the rule in `people/README.md`). The finder matches every alias, so old mentions still find the person. Obsidian also rewrites links on rename. `lint` reports links to a name that is neither a page nor an alias. |
| **Same name twice** | Two pages cannot have the same file name. The second person's page uses a middle initial or a suffix. `add-teammate` checks. |
| **Person who left** (`left:` on the page) | Not mentionable. Open mentions to them become a nightly review flag to the author: "Sam left. Give this to someone else or close it." |
| **Stale to-dos** | No due date and open more than 14 days: the finder shows them only as a count line ("and N more older than 14 days"). Open more than 30 days: the nightly review flags the author once: "still needed?". Nothing closes by itself. |
| **Noise** | Only lines that start with the mention count. Skip `skills/`, `templates/`, examples and code blocks. Cap at 10 lines. The same line seen in two copies (Windows skill copies) counts once. The full list shows once per day; later sessions that day show only the count and new items (state in the cache file). |
| **Logs folded by the nightly review** | Today the fold deletes daily logs older than 30 days and a model writes a summary. Open to-dos would be lost. Change: **the fold script (not the model) copies every open `- [ ]` line word for word into a `## Open to-dos` list at the end of the month summary, with a link back to the old file and line.** The finder reads summaries like any other note. A ticked box in a summary closes it as usual. |
| **Two people tick the same box at once** | The second push gets `re-apply`. `re-apply.md` already handles it: both changes are the same tick, so it resolves with no question. |
| **A mention inside a private-source note** | Section 4 of `AGENTS.md` applies. The ask must be a plain work ask. The push check and the nightly review already check this. |
| **Root content** | A mention at the root is held by sync step 6a like any root note. The hold message adds: "To ask everyone, use a 'Right now' line." |
| **Chat-only agents** (no disk) | They read from the host. They cannot run the finder. `AGENTS.md` says so in one line. The app (`[app]`) runs the finder on the server per person, under the same access. |

## 4. What happens to reports

### Drop the daily to-decide page

Its two inputs become mentions:

- **Review flags.** The nightly review writes each flag as a mention line in the area's log for that night: `areas/<area>/memory/logs/YYYY-MM-DD-review.md`, by the same `review/<date>` pull request it uses now.
  `- [ ] [[Jane Doe]] two notes disagree on the price: [[Price list 2026]] and [[Q4 offer]]`
  Day 2, still open: the review adds a line for the approver (area director, else the admin). Same escalation as today, now visible in the files.
  Company-repo flags go to `areas/<report_area>/memory/logs/` (default `admin`), never the root, the same rule as #66.
- **Rules pull requests waiting.** The review adds one mention per rules PR that waits more than one day: `- [ ] [[Admin Name]] approve rules PR 42 (invoice-skill-step)`. It closes the box itself when the PR is merged or closed. This is the only box a script ticks, and only for its own lines.
- **Possible leaks stay off the repo.** They stay in the admin's digest on the admin's computer, as today. Never a mention.
- The digest files in `~/.config/<company>-os/state/digests/` stay, for the admin's own record.

### Weekly "what happened": on demand by default

- `reports/run.sh --week` keeps all its rules (no ranking, no workspace, no private source). It prints the page to the chat by default. It writes no file.
- `--save` writes it to the asker's workspace (private), or with `--area` to `areas/<area>/reports/` by that area's PR.
- New switch `weekly-reports`: when on, the admin job writes the weekly area pages and the company page each Monday, as v1.0.7 does. Off by default for new companies.
- Why: an empty or unread weekly page is noise, and it failed the gates. People ask "what happened this week?" when they want it.

### What the nightly review does with mentions

1. Writes flags as mentions (above).
2. Flags mentions to a person who cannot read that area, to a person who left, or to a name that matches no page.
3. Flags mentions open more than 30 days, once.
4. Keeps open mentions when it folds logs (section 3).
5. Never ticks a box a person wrote. Never closes, moves or rewrites a person's mention.

The admin job becomes: nightly review, then `reports/run.sh --weekly-if-on`, which does nothing unless the switch is on.

## 5. Optional Claude Code plugin

### Where it lives

- In the company OS itself: `skills/claude-plugin/` (a plugin folder with `.claude-plugin/plugin.json`, `hooks/hooks.json` and small scripts). It is a local plugin marketplace. The company owns it, and it does not need this repo.
- `start-claude.md` and `add-teammate` offer it: "Do you want Claude Code to do the session-start steps by itself?" On yes, the person adds the marketplace and installs the plugin at user scope.
- User scope, not `.claude/settings.json` in a repo: area work starts in the area folder, and each area is its own repo. A user-scope plugin works in every folder. Its scripts walk up to `company-profile.md`, and do nothing outside a company folder.
- The plugin only calls the company scripts (`sync.sh`, `mentions.sh`). It holds no logic of its own. The scripts are the contract.

### Hooks

| Hook | What it does |
|---|---|
| `SessionStart` (startup, resume, clear) | Runs `sync.sh pull` (20-second limit; on time-out it says so and the agent runs it), `sync.sh status` and `mentions.sh`. Puts the output into context with one line: "Session start is done. Tell the person the held files and the mentions first." |
| `SessionStart` (compact) | After a compaction: mentions and held files again, from the cache. No pull. |
| `UserPromptSubmit` | Reads the cache only (fast). If a new mention came since the last turn (the 15-minute job found it), adds one line: "New mention for you: ...". Otherwise adds nothing. |
| Status line | `open mentions: 3` from the cache. A status line is the person's own setting, so setup offers to add it. If they already have one, the script prints only its part, for them to join. |
| `Stop` | If this session changed files in an area and today's log has no line from this session, it blocks the stop once with the reason "Write the log line first (AGENTS.md: Memory and logs)." It checks `stop_hook_active`, so it never loops. It does not push: push stays a sign-off step. |
| `PreCompact` | Reminds the agent to write the log line and keep open to-dos before the context is cut. |
| `PreToolUse` on `Bash` | Blocks: any `git push` to `main`; `git reset --hard`, `git clean -x` or `git rm -r` at the company root; `--no-verify`; a `gh` comment with `/approve` or `/override`; deleting the sync lock. Each block quotes the `AGENTS.md` rule. |
| `PreToolUse` on `Write`/`Edit` | Blocks: a new file at the company root that is not map, memory or a fact file (same list as sync step 6a); a write into another person's `users/<slug>/`; a file named `.env` or with a key-like name. Warns on a mention to a person who cannot read that area. |

The hooks are a convenience and a guard. They never replace the server checks (secret scan, review, owner gate) or the `AGENTS.md` rules.

### Other agents

- `AGENTS.md` stays the floor. Section 2 becomes: "At session start, run `sync.sh pull`, `sync.sh status` and `skills/mentions/mentions.sh`. Tell the person held files and open mentions first. If a plugin already did this, its output says so: do not run them again."
- The text "No vendor hooks" changes to "Hooks are optional. The scripts are the same either way." The rule stays true: nothing depends on a hook.
- Codex, Cursor, Grok and Pi read `AGENTS.md` and run the same scripts. An agent that has its own hooks may call the same scripts. The `start-<agent>.md` file says how, when the vendor supports it.

### Space in `AGENTS.md`

`template/AGENTS.md` is at 8,953 of 9,000 characters. The change must cost nothing:

- Section 2: add `mentions.sh` to the existing sentence. Change "No vendor hooks." to "Hooks are optional." About +40.
- Section 3 table: one new row, "A to-do or note for a teammate | `- [ ] [[Name]] <ask>` in an area you both can read. Everyone: a 'Right now' line." About +110.
- To pay for it: move the "Existing knowledge" section (about 330 characters) into `skills/ingest/` with a one-line pointer.

## 6. Migration from v1.0.7 and tests

### Migration (by `upgrade.sh --refresh`)

1. The refresh PR adds `skills/mentions/`, the new `AGENTS.md` lines, the new `reports` and `nightly-review` text, the fold change and `sync/jobs.sh`. Its body lists each change, as review-rules "Upgrade and refresh" asks.
2. `company-profile.md`: the refresh adds `weekly-reports` to `switches:` **for a company that upgrades**, so its weekly pages do not stop without a word. The PR body says: "Remove `weekly-reports` to make weekly pages on demand." New companies start without it.
3. `report_area:` stays. It now also names where company-repo review mentions go.
4. Old report files in `areas/*/reports/` stay as history. Nothing is deleted.
5. No conversion of to-decide pages: they are rebuilt each night, so the first nightly review after the upgrade writes the same items as mentions.
6. People pages: the refresh adds an empty `aliases: []` to each teammate page that has none (a map change at the root, so it waits for `/approve` with the rest).
7. The admin job command changes from `nightly-review && reports` to `nightly-review && reports --weekly-if-on`. `install-jobs --admin` rewrites it. The refresh tells the admin to run it once. Until then the old command still works (old flags stay valid).
8. The plugin is not installed by the upgrade. The admin is told it exists. Each person chooses.

### Tests

- `tests/mentions/` with an Acme fixture: a company with three areas, people pages with aliases, one teammate who left, one customer contact.
  - open, ticked, and "link not first" lines; `*` and `-` bullets; alias links `[[Name|x]]`; two names on one line.
  - skipped folders and fenced code; untracked notes counted; ignored files not.
  - an area not on disk gives no hit; an area in its lost-access window is marked.
  - `me` missing; page missing; a broken repo prints `not read` and exit 0.
  - sort order, the 10-line cap, `--count`, `--all`, `--json` shape.
  - speed: a generated company with 50,000 files finishes in under 2 seconds.
  - Windows: the same cases under Git Bash (`tests/windows`).
- `test_nightly.py`: flags written as mentions; day-2 escalation; rules-PR mention opened and closed by the review; company flags go to `report_area`; possible leaks never in a file; the fold keeps open boxes word for word; never ticks a person's box.
- `test_reports`: on-demand prints and writes nothing; `--save` paths; `weekly-reports` on keeps the v1.0.7 behavior.
- `test_refresh.py`: a v1.0.7 company upgrades; switch added; aliases added; old reports kept; refresh body lists everything.
- Plugin: each hook script fed JSON on stdin; no-op outside a company folder; `Stop` blocks once and never loops; each guard blocks its case and lets a normal case through.
- Static: `AGENTS.md` under the cap; placeholders; PII check; shellcheck on `mentions.sh` and the hook scripts.
- End to end, per the repo rule: a fresh setup in a new user account with Claude Cowork and Claude Code. One teammate writes a mention; the other sees it at session start within 15 minutes of the push.
